# Rule-Based Recommendation Builder

## Назначение

`RuleBasedRecommendationBuilder` преобразует одну подтверждённую `BusinessOpportunity` в список объяснимых `Recommendation`.

Компонент работает внутри **Revenue Intelligence Layer** и принимает решение только по данным возможности:

- `opportunity_type`;
- `urgency`;
- `confidence`;
- `detected_entities`;
- `evidence`.

Результат детерминирован: при одинаковом входе Builder возвращает одинаковый список рекомендаций.

## Архитектура

```text
BusinessOpportunity
    ├── тип возможности
    ├── срочность
    ├── уверенность
    ├── найденные сущности
    └── доказательства
              │
              ▼
RuleBasedRecommendationBuilder
              │
              ▼
list[Recommendation]
```

Builder не подключён к `RevenueIntelligenceEngine`, существующему Pipeline, Scheduler, API-слою или сервисам приложения. Его можно внедрить позднее через уже существующий интерфейс `RecommendationBuilder`.

## Контракт рекомендации

Каждая `Recommendation` содержит:

| Поле | Назначение |
|---|---|
| `action_type` | Стабильный тип действия |
| `title` | Короткое название действия |
| `description` | Что нужно сделать |
| `reason` | Объяснение, какое правило применилось |
| `priority` | `low`, `medium`, `high` или `critical` |
| `deadline` | Детерминированный дедлайн из срочности |
| `expected_result` | Ожидаемый операционный результат без обещания дохода |
| `required_entities` | Сущности, необходимые для действия |
| `supporting_evidence` | Доказательства из возможности |
| `supporting_signal_ids` | Идентификаторы исходных сигналов |

Поля `action`, `rationale` и `expected_effect` сохранены как read-only совместимые свойства для контрактов RC2.2.

## Поддерживаемые действия

| `action_type` | Когда формируется |
|---|---|
| `call_clients` | `retention` или подтверждённый сегмент/аудитория для роста |
| `send_email_campaign` | Подтверждённый сегмент, аудитория или клиенты для роста |
| `send_messenger_campaign` | `retention` или подтверждённый канал мессенджера |
| `publish_social_media_post` | Подтверждённая сущность социальной сети |
| `update_website_banner` | Подтверждённая сущность сайта или лендинга |
| `notify_sales_manager` | `pricing`, `cost_saving`, `operational` |
| `create_crm_task` | `retention`, `pricing`, `cost_saving`, `operational` |
| `contact_tour_operator` | `pricing` с сущностью `tour_operator` |
| `monitor_promotion` | Низкая или средняя срочность подтверждённой возможности |
| `escalate_urgent_opportunity` | Критическая срочность |
| `wait` | Низкая уверенность при срочности выше `low` |
| `ignore` | Низкая уверенность и низкая срочность |

## Правила формирования

1. **Доказательства обязательны.** Если `evidence` пустой, Builder возвращает `[]`.
2. **Низкая уверенность блокирует активные действия.**
   - `low` urgency → `ignore`;
   - любая более высокая срочность → `wait`.
3. **Критическая срочность всегда эскалируется.** Дополнительно к правилам типа создаётся `escalate_urgent_opportunity`.
4. **Каналы не угадываются.** Маркетинговое действие создаётся только при соответствующей сущности:
   - сегмент/аудитория → звонки и email;
   - мессенджер → мессенджер-кампания;
   - социальная сеть → пост;
   - сайт/лендинг → баннер.
5. **Приоритет зависит только от срочности и уверенности.**
   - `critical` → `critical`;
   - `high` → `high`;
   - `medium` + `high confidence` → `high`;
   - `medium` → `medium`;
   - `low` → `low`.
6. **Дедлайн зависит только от `created_at` и срочности.**
   - `critical`: +4 часа;
   - `high`: +24 часа;
   - `medium`: +72 часа;
   - `low`: отсутствует.
7. **Дубликаты объединяются.** Совпадающие `action_type` и `title` сливаются; сущности, доказательства и ID сигналов объединяются без повторов.

## Границы ответственности

Builder **не**:

- вызывает LLM, AI-модели или статистические модели;
- использует CRM, историю клиентов или персональные данные;
- запрашивает внешние API;
- строит финансовые прогнозы;
- отправляет сообщения, посты, email или уведомления;
- создаёт задачи в реальной CRM;
- изменяет `BusinessOpportunity`;
- меняет или подключается к существующему Pipeline;
- изменяет `RevenueScoringService`, `FilteringService`, `MorningBriefService`, `DecisionCardService` или `Scheduler`.

`Create CRM Task` — это только описание будущего действия. Интеграция с CRM находится вне scope RC2.3.

## Будущие расширения

RC2.4 может добавить отдельный `Revenue Estimation` компонент, который будет оценивать диапазон результата, не меняя правила Builder.

После отдельного архитектурного решения возможны:

- внедрение Builder в `RevenueIntelligenceEngine`;
- таблица правил, загружаемая из конфигурации;
- исполнители действий с явным подтверждением пользователя;
- отдельная интеграция CRM;
- журнал решений и пользовательская обратная связь.

Все расширения должны сохранять объяснимость, детерминированность и изоляцию от существующего Pipeline.
