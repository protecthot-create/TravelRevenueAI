# Implementation Plan — MVP Travel Revenue AI

## Проект
Travel Revenue AI — внешний интеллект для турагентств, который находит денежные возможности, предупреждает о рисках и превращает рыночные сигналы в конкретные действия.

## Цель MVP
Собрать минимально полезную версию продукта, которая:
- принимает внешние и внутренние сигналы;
- оценивает их по деньгам, срочности, вероятности и управляемости;
- отфильтровывает шум;
- формирует короткий утренний бриф;
- показывает 3–5 приоритетных действий на сегодня.

## Принципы MVP
1. Деньги важнее шума.
2. Риски важнее возможностей при равной сумме.
3. Каждое рекомендованное действие должно быть конкретным.
4. В утреннем брифе только короткий actionable output.
5. Сложные и долгие действия разбиваются на этапы.
6. Для старта лучше меньше источников, но выше качество сигналов.

## Scope MVP

### Входит в MVP
- модель сигналов;
- оценка важности и score;
- фильтрация шумов;
- классификация на возможность / риск / рынок / операционный сигнал;
- генерация рекомендаций и дедлайна;
- формирование утреннего брифинга;
- базовая настройка источников;
- ручной или полуавтоматический ввод сигналов;
- минимальная аналитика по результатам рекомендаций.

### Не входит в MVP
- полноценная CRM;
- бронирование туров;
- сложная автоматизация всех источников;
- продвинутый personalisation engine;
- сложный multi-agent orchestration;
- глубокая историческая оптимизация;
- расширенная BI-панель;
- сложная интеграция с десятками внешних API.

## MVP-архитектура
1. **Ingest layer** — получение сигналов вручную или через простые коннекторы.
2. **Normalize layer** — приведение сигнала к общему формату.
3. **Scoring layer** — расчёт score, важности и confidence.
4. **Filtering layer** — отбраковка шума и слабых сигналов.
5. **Action layer** — генерация конкретного действия с дедлайном.
6. **Brief layer** — сборка утреннего брифа.
7. **Feedback layer** — фиксация реакции пользователя для последующей калибровки.

## Этапы разработки

### Этап 1. Зафиксировать ядро продукта
**Результат:** понятная модель того, что именно считается сигналом, действием и брифом.

Задачи:
- определить типы сигналов;
- зафиксировать единый JSON/DTO формат сигнала;
- определить поля для money, urgency, probability, controllability, deadline, confidence;
- описать правила перевода сигнала в действие;
- согласовать формат output для брифа.

### Этап 2. Реализовать scoring и filtering
**Результат:** система умеет отличать шум от денег.

Задачи:
- реализовать score на базе `docs/scoring_rules.md` и `docs/revenue_score.md`;
- внедрить правила фильтрации из `docs/filtering_rules.md` и `docs/money_action_filter.md`;
- учесть приоритет риска над возможностью;
- добавить пороги для малых и средних агентств;
- поддержать объяснение, почему сигнал прошёл или был отклонён.

### Этап 3. Построить генерацию рекомендаций
**Результат:** на выходе не абстрактный анализ, а конкретное действие.

Задачи:
- превращать сигнал в рекомендацию;
- ограничивать рекомендации по времени выполнения;
- добавлять дедлайн;
- формировать короткое объяснение пользы;
- указывать риск бездействия для risk-сигналов.

### Этап 4. Собрать утренний бриф
**Результат:** продукт выдаёт ежедневный actionable summary.

Задачи:
- собрать top-5 возможностей;
- собрать top-3 риска;
- выделить 1 главное действие дня;
- убрать шум и дубли;
- обеспечить короткий и ясный формат по `docs/morning_brief.md`.

### Этап 5. Добавить источники сигналов
**Результат:** MVP получает сигналы из минимального набора источников.

Задачи:
- выбрать 3–5 внутренних источников;
- выбрать 3–5 рыночных источников;
- выбрать 2–3 поведенческих источника;
- выбрать 2–3 операционных источника;
- настроить приоритеты источников по довериям из `docs/sources.md`.

### Этап 6. Подключить обратную связь
**Результат:** система учится на реакции пользователя.

Задачи:
- фиксировать, выполнено ли действие;
- фиксировать, было ли оно полезным;
- фиксировать причины отклонения;
- использовать feedback для калибровки score и фильтров;
- хранить историю изменений правил.

### Этап 7. Проверить MVP на тест-кейсах
**Результат:** базовая логика проходит сценарии из `docs/test.md`.

Задачи:
- прогнать кейсы на раннее бронирование;
- проверить отбраковку шумовых новостей;
- проверить конфликт сигналов;
- проверить приоритет риска;
- проверить поведение на серии мелких сигналов;
- проверить, что длинные действия не попадают в top priority без разбивки.

## Рекомендуемый порядок реализации
1. Формат данных сигнала.
2. Scoring.
3. Filtering.
4. Action generation.
5. Morning brief.
6. Sources.
7. Feedback.
8. Validation against test cases.

## Definition of Done для MVP
MVP считается готовым, если:
- сигнал можно нормализовать в общий формат;
- score считается предсказуемо;
- шум отсекается;
- риск имеет приоритет над возможностью;
- на выходе есть конкретное действие;
- утренний бриф содержит 3–5 полезных пунктов;
- тест-кейсы проходят;
- пользователь может дать feedback.

## Риски и ограничения
- слишком много слабых сигналов может засорить бриф;
- плохое качество источников ухудшит score;
- без feedback калибровка будет медленной;
- если action output слишком длинный, ценность продукта падает;
- без жёсткого фильтра MVP превратится в новостную ленту.
