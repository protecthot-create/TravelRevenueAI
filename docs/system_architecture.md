# System Architecture — Travel Revenue AI

## Проект
Travel Revenue AI — внешний интеллект для турагентств, который превращает сигналы рынка и внутренние данные в приоритетные денежные действия.

## Назначение документа
Этот документ описывает техническое устройство системы Travel Revenue AI на уровне компонентов и потоков данных. Он опирается на:
- `docs/vision.md`
- `docs/implementation_plan.md`
- существующие правила и доменную архитектуру проекта

Код в этом документе не приводится.

## Архитектурный принцип
Система строится как конвейер:
1. получает сигнал;
2. приводит его к общему формату;
3. оценивает денежную ценность и срочность;
4. отбрасывает шум;
5. формирует конкретную рекомендацию;
6. собирает утренний бриф;
7. сохраняет реакцию пользователя для улучшения качества.

## Компоненты системы

### 1. Signal Ingestion

**Назначение**  
Сбор сигналов из внешних и внутренних источников в единую входную точку системы.

**Входные данные**  
- сырые сигналы из источников данных;
- ручной ввод пользователя или оператора;
- данные из простых интеграций и коннекторов;
- события по расписанию.

**Выходные данные**  
- сырой сигнал в промежуточном формате;
- метаданные источника;
- отметка времени;
- идентификатор типа сигнала.

**Взаимодействие с другими компонентами**  
- получает данные от источников;
- передаёт сигнал в Data Normalization;
- может запускаться Scheduler-ом;
- пишет события в Database для аудита.

**Обязателен для MVP**  
Да.

---

### 2. Data Normalization

**Назначение**  
Приведение сырых сигналов к единому структурированному формату, пригодному для scoring и filtering.

**Входные данные**  
- сырой сигнал из Signal Ingestion;
- данные источника;
- контекст агентства, если он доступен.

**Выходные данные**  
- нормализованный сигнал;
- унифицированные поля:
  - тип сигнала;
  - денежный эффект;
  - срочность;
  - вероятность;
  - управляемость;
  - дедлайн;
  - confidence;
- признаки неполноты данных.

**Взаимодействие с другими компонентами**  
- получает данные из Signal Ingestion;
- передаёт нормализованный сигнал в Revenue Scoring Engine;
- сохраняет результат нормализации в Database.

**Обязателен для MVP**  
Да.

---

### 3. Revenue Scoring Engine

**Назначение**  
Расчёт score и приоритета сигнала на основе денежного потенциала, срочности, вероятности и управляемости.

**Входные данные**  
- нормализованный сигнал;
- контекст агентства;
- исторические или пользовательские поправки, если они уже есть.

**Выходные данные**  
- score;
- priority label;
- confidence;
- объяснение расчёта;
- дополнительные признаки, важные для фильтрации.

**Взаимодействие с другими компонентами**  
- получает данные из Data Normalization;
- отдаёт результат в Filtering Engine;
- использует правила из существующих scoring-документов;
- пишет score в Database;
- может быть переиспользован в Feedback & Learning для калибровки.

**Обязателен для MVP**  
Да.

---

### 4. Filtering Engine

**Назначение**  
Отбор сигналов, которые действительно несут денежную ценность, и отбрасывание шума, слабых или противоречивых сигналов.

**Входные данные**  
- сигнал со score;
- признаки типа сигнала;
- пороги фильтрации;
- контекст агентства;
- дополнительные ограничения из правил.

**Выходные данные**  
- решение: pass / reject / needs review;
- причина прохождения или отклонения;
- категория отклонения, если сигнал не прошёл;
- метка конфликтности, если сигнал противоречит другим.

**Взаимодействие с другими компонентами**  
- получает данные из Revenue Scoring Engine;
- передаёт прошедшие сигналы в Recommendation Engine;
- может отправлять отклонённые сигналы в Database для анализа качества;
- использует правила фильтрации как источник истины.

**Обязателен для MVP**  
Да.

---

### 5. Recommendation Engine

**Назначение**  
Преобразование прошедшего фильтр сигнала в конкретное, короткое и выполнимое действие.

**Входные данные**  
- сигнал, прошедший Filtering Engine;
- score;
- тип сигнала;
- дедлайн;
- ограничения по времени;
- risk context.

**Выходные данные**  
- конкретная рекомендация;
- ожидаемый денежный эффект;
- дедлайн;
- краткое объяснение;
- риск бездействия для risk-сигналов;
- ссылка на исходный сигнал.

**Взаимодействие с другими компонентами**  
- получает данные из Filtering Engine;
- передаёт рекомендации в Morning Brief Generator;
- сохраняет итоговую рекомендацию в Database;
- передаёт метаданные в Feedback & Learning после реакции пользователя.

**Обязателен для MVP**  
Да.

---

### 6. Morning Brief Generator

**Назначение**  
Формирование краткого ежедневного брифа с приоритетными возможностями, рисками и главным действием дня.

**Входные данные**  
- список рекомендаций;
- список приоритетных рисков;
- score и priority label;
- правила форматирования брифа;
- контекст по дню и пользователю.

**Выходные данные**  
- готовый morning brief;
- top-5 возможностей;
- top-3 риска;
- одно главное действие;
- краткий формат для доставки пользователю.

**Взаимодействие с другими компонентами**  
- получает данные из Recommendation Engine;
- может читать сохранённые сигналы из Database;
- выдаёт готовый brief в Frontend и/или API;
- сохраняет сформированный бриф в Database.

**Обязателен для MVP**  
Да.

---

### 7. Feedback & Learning

**Назначение**  
Сбор обратной связи пользователя и использование её для улучшения scoring, filtering и рекомендаций.

**Входные данные**  
- факт выполнения действия;
- оценка полезности;
- ручной фидбек пользователя;
- причины отклонения рекомендации;
- поведенческие сигналы по использованию интерфейса.

**Выходные данные**  
- feedback record;
- корректировки для score и фильтров;
- сигналы для переоценки порогов;
- данные для аналитики качества.

**Взаимодействие с другими компонентами**  
- получает данные из Frontend и API;
- обновляет контекст для Revenue Scoring Engine и Filtering Engine;
- пишет историю обратной связи в Database;
- может использоваться Scheduler-ом для периодической калибровки.

**Обязателен для MVP**  
Да, в минимальном виде.

---

### 8. Scheduler

**Назначение**  
Управление периодическими и триггерными задачами системы.

**Входные данные**  
- расписание;
- триггеры обновления;
- список источников;
- задачи на генерацию брифа;
- задачи на калибровку и проверку.

**Выходные данные**  
- запуск ingestion;
- запуск scoring и filtering;
- запуск morning brief;
- периодические job-ивенты;
- события для повторной обработки.

**Взаимодействие с другими компонентами**  
- запускает Signal Ingestion;
- инициирует сбор утреннего брифа;
- может инициировать пересчёт score;
- запускает фоновую обработку feedback;
- использует Database для состояния задач.

**Обязателен для MVP**  
Да, но может быть очень простым.

---

### 9. Database

**Назначение**  
Централизованное хранение данных системы и истории действий.

**Входные данные**  
- сырые сигналы;
- нормализованные сигналы;
- score и фильтрационные решения;
- рекомендации;
- morning brief;
- feedback;
- настройки источников;
- метаданные задач.

**Выходные данные**  
- данные для API;
- данные для аналитики;
- история изменений;
- данные для калибровки;
- данные для воспроизведения принятия решений.

**Взаимодействие с другими компонентами**  
- используется всеми слоями;
- хранит устойчивое состояние системы;
- поддерживает аудит, аналитику и повторную генерацию;
- служит источником данных для Frontend и API.

**Обязателен для MVP**  
Да.

---

### 10. API

**Назначение**  
Единая точка доступа для Frontend, интеграций и внешних клиентов.

**Входные данные**  
- запросы от Frontend;
- события от Scheduler;
- фидбек от пользователя;
- внешние запросы на получение брифа или сигналов.

**Выходные данные**  
- данные о сигналах;
- рекомендации;
- утренний бриф;
- данные feedback;
- статусы задач;
- ответы на чтение и обновление данных.

**Взаимодействие с другими компонентами**  
- читает и пишет в Database;
- вызывает внутренние компоненты системы;
- отдаёт данные в Frontend;
- принимает feedback;
- может быть точкой интеграции для будущих внешних каналов.

**Обязателен для MVP**  
Да.

---

### 11. Frontend

**Назначение**  
Интерфейс для просмотра сигналов, рекомендаций, morning brief и обратной связи.

**Входные данные**  
- данные из API;
- краткие брифы;
- список рекомендаций;
- статусы и объяснения;
- формы обратной связи.

**Выходные данные**  
- действия пользователя в интерфейсе;
- feedback;
- подтверждение выполнения задач;
- запросы на обновление данных.

**Взаимодействие с другими компонентами**  
- работает через API;
- показывает результаты Ingestion, Scoring, Filtering и Recommendation;
- передаёт обратную связь в Feedback & Learning;
- может показывать историю сигналов и решений.

**Обязателен для MVP**  
Да, если MVP включает пользовательский интерфейс. Минимальная версия может быть очень простой, но должна позволять просматривать бриф и оставлять feedback.

## Рекомендуемая зависимость компонентов
Поток обработки должен идти в следующем порядке:

1. Signal Ingestion  
2. Data Normalization  
3. Revenue Scoring Engine  
4. Filtering Engine  
5. Recommendation Engine  
6. Morning Brief Generator  
7. Frontend / delivery layer  
8. Feedback & Learning  
9. Scheduler оркестрирует запуск процесса  
10. Database хранит всё состояние  
11. API связывает остальные слои

## Обязательность компонентов для MVP

| Signal Ingestion | Обязателен |
| Data Normalization | Обязателен |

| Filtering Engine | Обязателен |

| Morning Brief Generator | Обязателен |
| Feedback & Learning | Обязателен в минимальном виде |
| Scheduler | Обязателен, может быть простым |

## Схема потока данных

Источник данных → Ingestion → Normalization → Scoring → Filtering → Recommendation → Morning Brief → Пользователь → Feedback

## Примечания по MVP-реализации
- На старте компоненты могут быть логически разделены, даже если физически реализованы в одном сервисе.
- Для MVP не требуется микросервисная сложность.
- Ключевая цель архитектуры — предсказуемость, прозрачность решений и возможность калибровки.
- Все компоненты должны сохранять объяснимость результата: почему сигнал прошёл, почему был отклонён и почему была предложена именно эта рекомендация.
